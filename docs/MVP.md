# نقشه MVP — ایجنت تعمیر فلش USB ویندوزی

نسخه: 1.0 — تاریخ: 2026-10-23 — وضعیت: آماده پیاده‌سازی
مخاطب سند: فرزاد (مالک محصول) + ایجنت/توسعه‌دهنده پیاده‌ساز

---

## ۱) خلاصه اجرایی

محصول، یک نرم‌افزار ویندوزی است که کاربر در آن نشانی پایه و کلید مدل هوش مصنوعی خودش را وارد می‌کند و نرم‌افزار به‌صورت ایجنت، فلش متصل را مرحله‌به‌مرحله بررسی، عیب‌یابی و — فقط با تأیید کاربر در قدم‌های مخرب — تعمیر می‌کند.

تمایز محصول در خودِ مدل نیست. تمایز در سه چیز است: یک) ابزارهای واقعی و تست‌شده تعمیر، دو) دروازه ایمنی که جلوی نابودی اشتباهی داده و بریک شدن فلش را می‌گیرد، سه) تجربه کاربری ساده و فارسی/انگلیسی به‌جای ابزارهای کارخانه‌ای پیچیده و چینی.

قاعده طلایی طراحی که در کل سند حاکم است: مدل هرگز دستور خام اجرا نمی‌کند. مدل فقط از فهرست بسته ابزارهای از پیش ساخته‌شده انتخاب می‌کند، برای هر انتخاب دلیل می‌آورد، و اجرای هر ابزار از فیلتر ایمنی و تأیید متناسب با سطح ریسک رد می‌شود.

## ۲) مسئله و کاربر هدف

کاربر هدف اول، تعمیرکار موبایل/کامپیوتر و کاربر نیمه‌حرفه‌ای است که فلش‌هایی با این نشانه‌ها می‌آورد: باز نشدن در ویندوز، درخواست فرمت مداوم، ظرفیت صفر یا اشتباه، قفل نوشتن، کندی شدید، فایل‌های خراب یا ظرفیت جعلی.

کاربر هدف دوم، کاربر عادی است که فقط گزارش روشن می‌خواهد: مشکل چیست، داده‌اش قابل نجات هست یا نه، و تعمیر چقدر شانس دارد.

## ۳) محدوده MVP — داخل و خارج

### داخل محدوده نسخه اول

- شناسایی خودکار همه فلش‌ها و دیسک‌های قابل‌حمل متصل، با نمایش امن برای انتخاب دستگاه درست
- عیب‌یابی کامل فقط‌خواندنی بدون هیچ تغییری روی فلش، همراه با گزارش ساخت‌یافته
- دسته‌بندی خرابی در پنج گروه مشخص: خرابی فایل‌سیستم، خرابی پارتیشن، قفل نوشتن نرم‌افزاری، ظرفیت جعلی/اشتباه، نشانه‌های خرابی فریمور یا کنترلر
- تعمیرهای امن با تأیید کاربر: پشتیبان از جدول پارتیشن، ساخت دوباره پارتیشن، فرمت درست، رفع پرچم قفل نوشتن، بررسی و رفع خطای فایل‌سیستم
- شناسایی خانواده کنترلر برای خانواده‌های رایج بازار و اعلام شفاف اینکه تعمیر فریموری آن خانواده در نسخه اول پشتیبانی می‌شود یا فقط گزارش داده می‌شود
- گزارش نهایی قابل ذخیره برای هر تعمیر: دستگاه، تشخیص، قدم‌های اجراشده، نتیجه راستی‌آزمایی
- پشتیبانی از هر مدل سازگار با رابط استاندارد گفتگو و فراخوانی ابزار، با نشانی پایه و کلید قابل تنظیم توسط کاربر؛ قفل نبودن به هیچ شرکت یا مدل خاص

### خارج از محدوده نسخه اول

- فلش فریمور به‌صورت عمومی برای همه کنترلرها؛ این قابلیت فقط در فاز سوم و فقط خانواده‌به‌خانواده اضافه می‌شود
- ریکاوری داده در سطح آزمایشگاهی، تعمیر فیزیکی، یا کار با فلشی که اصلاً در سیستم شناسایی نمی‌شود
- اجرای خودکار و بدون تأیید هر اقدام مخرب
- دور زدن امضای فریمور، دست‌کاری ظرفیت برای ساخت فلش جعلی، یا هر قابلیت فریب کاربر نهایی

## ۴) معیار موفقیت MVP

- عیب‌یابی فقط‌خواندنی روی هر فلش سالم و خراب، بدون هیچ نوشتن روی دستگاه، در کمتر از ۶۰ ثانیه کامل شود
- در تست با حداقل ۲۰ فلش نمونه دارای خرابی معلوم، دسته‌بندی خرابی حداقل در ۸۵٪ موارد با واقعیت یکی باشد
- هیچ اقدام مخربی در هیچ سناریویی بدون تأیید صریح و ثبت‌شده کاربر اجرا نشود؛ این مورد معیار خط قرمز است و تست خودکار دارد
- کاربر غیرمتخصص بتواند فقط با خواندن گزارش، مشکل و شانس تعمیر و سرنوشت داده‌ها را بفهمد

## ۵) معماری سیستم

معماری از پنج لایه جدا ساخته می‌شود تا مدل، ابزار و رابط کاربری هیچ‌کدام جای دیگری تصمیم نگیرد:

- لایه رابط کاربری، فقط نمایش و گرفتن تأیید است؛ هیچ منطق تعمیری داخل دکمه‌ها زندگی نمی‌کند
- لایه ایجنت، چرخه مشاهده ← تحلیل ← انتخاب ابزار ← راستی‌آزمایی را می‌گرداند و سقف قدم و سقف زمان دارد
- لایه دروازه ایمنی، قبل از اجرای هر ابزار، سطح ریسک، دستگاه هدف و تطابق تأیید کاربر را بررسی می‌کند و در صورت مغایرت اجرا را متوقف می‌کند
- لایه ابزارها، برنامه‌های کوچک و مستقل و قطعی هستند که هر کدام یک کار مشخص را با ورودی و خروجی ساخت‌یافته انجام می‌دهند
- لایه ارائه‌دهنده مدل، ارتباط با مدل را پشت یک قرارداد واحد پنهان می‌کند تا تعویض مدل یا نشانی پایه، بقیه سیستم را تغییر ندهد

### چرخه اجرای ایجنت

چرخه برای هر نشست تعمیر به این ترتیب است و هر دور آن در لاگ نشست ثبت می‌شود:

1. قدم مشاهده: ابزارهای فقط‌خواندنی اجرا می‌شوند و وضعیت دستگاه به‌صورت داده ساخت‌یافته جمع می‌شود
2. قدم تحلیل: مدل بر اساس داده‌ها فرضیه خرابی و درجه اطمینان می‌دهد؛ اطمینان پایین یعنی سؤال از کاربر یا تست بیشتر، نه حدس اجرایی
3. قدم برنامه: مدل برنامه مرحله‌ای پیشنهاد می‌کند و برای هر قدم، ابزار، دلیل و پیامد احتمالی را اعلام می‌کند
4. قدم تأیید: قدم‌های امن خودکار جلو می‌روند؛ قدم مخرب روی صفحه تأیید می‌ایستد تا کاربر صریحاً تأیید کند
5. قدم اجرا و راستی‌آزمایی: بعد از هر ابزار، تست راستی‌آزمایی اجرا می‌شود و نتیجه واقعی — نه ادعای مدل — مبنای قدم بعدی است
6. قدم گزارش: نشست با گزارش نهایی بسته می‌شود؛ موفقیت فقط وقتی اعلام می‌شود که راستی‌آزمایی نهایی سبز باشد

### تنظیمات مدل — قرارداد ورودی کاربر

کاربر سه مقدار می‌دهد و نرم‌افزار قبل از اولین استفاده، اتصال را با یک فراخوانی آزمایشی ارزان امتحان می‌کند:

```text
Base URL   : e.g. https://api.openai.com/v1  |  http://localhost:11434/v1 (local)
API Key    : stored ONLY in Windows DPAPI-protected storage, never in logs/config plaintext
Model Name : free text, user-chosen; app must not hardcode a vendor model list
```

الزامات این بخش: پشتیبانی از فراخوانی ابزار بومی مدل در اولویت است؛ اگر مدلی فراخوانی ابزار نداشت، حالت جایگزین با خروجی ساخت‌یافته متنی فعال می‌شود و ایجنت با همان ابزارها ولی با اعتبارسنجی سخت‌گیرانه‌تر کار می‌کند. دما برای تصمیم‌های تعمیری پایین و ثابت است. سقف هزینه و سقف دور چرخه برای هر نشست قابل تنظیم و دارای مقدار پیش‌فرض محافظه‌کارانه است.

### دروازه ایمنی — قوانین غیرقابل دور زدن

- قانون دستگاه هدف: هر ابزار مخرب، شناسه یکتای دستگاه را در لحظه اجرا دوباره بررسی می‌کند؛ اگر دیسک انتخاب‌شده با دیسک تأییدشده یکی نبود، اجرا لغو می‌شود
- قانون دیسک سیستمی: دیسک سیستم و دیسک‌های داخلی ثابت، برای همیشه از فهرست هدف‌های مخرب حذف‌اند و مدل هم اجازه انتخاب آن‌ها را ندارد
- قانون تأیید پلکانی: ریسک سطح ۲ یک تأیید می‌خواهد؛ ریسک سطح ۳ دو تأیید و نمایش هشدار پاک شدن قطعی داده و احتمال بریک شدن می‌خواهد
- قانون توقف: کاربر در هر لحظه می‌تواند نشست را متوقف کند؛ بعد از شروع نوشتن فریمور، توقف فقط در نقاط امن تعریف‌شده ممکن است و این محدودیت قبل از شروع به کاربر گفته می‌شود
- قانون لاگ پاک: کلید مدل، مسیرهای خصوصی کاربر و محتوای فایل‌های روی فلش هرگز وارد لاگ و گزارش نمی‌شوند

## ۶) سطوح ریسک ابزارها

- سطح ۰ — فقط‌خواندنی: هیچ نوشتنی روی دستگاه انجام نمی‌شود؛ اجرای خودکار آزاد است
- سطح ۱ — نوشتن برگشت‌پذیر و کم‌خطر: مثل نوشتن فایل آزمایشی موقت یا رفع پرچم نرم‌افزاری؛ اجرای خودکار با اطلاع کاربر
- سطح ۲ — مخرب ولی استاندارد: داده روی فلش از بین می‌رود ولی دستگاه بریک نمی‌شود؛ یک تأیید صریح لازم است
- سطح ۳ — مخرب و پرریسک: احتمال بریک شدن دائمی وجود دارد؛ دو تأیید، پشتیبان اطلاعات دستگاه و نمایش دقیق فایل فریمور لازم است

## ۷) فهرست کامل ابزارهای ایجنت

قرارداد مشترک همه ابزارها: هر ابزار یک نام یکتا، ورودی ساخت‌یافته، خروجی ساخت‌یافته، کد خطای استاندارد و مدت زمان سقف دارد. خروجی خام و طولانی ابزار هرگز مستقیم به مدل داده نمی‌شود؛ لایه ابزار آن را خلاصه و ساخت‌یافته می‌کند.

### گروه الف — تشخیص فقط‌خواندنی (ریسک ۰)

مشخصات این گروه در جدول زیر آمده است و همه اعضایش بدون تأیید اجرا می‌شوند:

| # | نام ابزار | کار | ورودی کلیدی | خروجی کلیدی | پیاده‌سازی ویندوزی |
|---|-----------|-----|--------------|--------------|---------------------|
| 1 | `list_usb_devices` | فهرست دیسک‌های قابل‌حمل با شناسه یکتا، مدل، ظرفیت اعلامی و حرف درایو | — | فهرست دستگاه‌ها | SetupAPI + IOCTL_STORAGE_QUERY_PROPERTY |
| 2 | `get_device_details` | جزئیات یک دستگاه: سازنده، شماره سریال، نسخه پروتکل، قابل‌حمل بودن | device_id | رکورد دستگاه | DeviceIoControl |
| 3 | `get_disk_layout` | خواندن جدول پارتیشن و وضعیت تخصیص، بدون تغییر | device_id | نوع جدول، پارتیشن‌ها، فضای خام | IOCTL_DISK_GET_DRIVE_LAYOUT_EX |
| 4 | `check_filesystem` | بررسی سلامت فایل‌سیستم در حالت فقط‌خواندن | device_id, volume | سالم / خراب / خام / ناشناخته + خلاصه خطا | FSCTL + chkdsk حالت خواندنی |
| 5 | `read_test_sample` | خواندن نمونه‌ای از ابتدا، وسط و انتهای دیسک برای کشف نواحی مرده | device_id | نقشه سلامت نمونه‌ای | خواندن سکتوری مستقیم |
| 6 | `detect_fake_capacity_risk` | مقایسه ظرفیت اعلامی با رفتار واقعی خواندن در انتهای دیسک | device_id | امتیاز ریسک ظرفیت جعلی | تست نمونه‌ای انتهای آدرس‌دهی |
| 7 | `identify_controller` | حدس مستند خانواده کنترلر از روی مشخصات دستگاه و پایگاه داده محلی | device_id | خانواده، درجه اطمینان، منبع حدس | پایگاه داده محلی مشخصات |
| 8 | `lookup_firmware_catalog` | جستجو در بانک محلی فریمور برای کنترلر شناسایی‌شده | controller_family, nand_hint | نامزدها + هش فایل + وضعیت تست | بانک محلی نسخه‌دار |
| 9 | `get_device_history` | سابقه تعمیر همین دستگاه در همین سیستم | serial | نشست‌های قبلی و نتایج | ذخیره محلی برنامه |

### گروه ب — تست فعال کم‌خطر (ریسک ۱)

- ابزار `write_test_temp` یک فایل آزمایشی کوچک با الگوی معلوم می‌نویسد، می‌خواند و مقایسه می‌کند، بعد پاکش می‌کند؛ قفل نوشتن واقعی و خطای نوشتن را قطعی می‌کند، نه با حدس
- ابزار `measure_speed_sample` سرعت خواندن و نوشتن ترتیبی را روی نمونه کوچک می‌سنجد تا کندی غیرعادی و افت انتهای دیسک دیده شود
- ابزار `clear_readonly_flag` پرچم فقط‌خواندنی نرم‌افزاری دیسک و رجیستری را بررسی و در صورت نرم‌افزاری بودن رفع می‌کند؛ اگر قفل از کنترلر باشد، صریحاً اعلام می‌کند که این ابزار کافی نیست

### گروه ج — تعمیر استاندارد (ریسک ۲ — یک تأیید)

| # | نام ابزار | کار | پیش‌نیاز اجباری | راستی‌آزمایی بعد از اجرا |
|---|-----------|-----|-------------------|---------------------------|
| 10 | `backup_partition_table` | پشتیبان باینری از جدول پارتیشن و سکتورهای آغازین در پوشه نشست | — (خودش ریسک ۰ است ولی دروازه گروه ج است) | خواندن دوباره و تطابق هش |
| 11 | `repair_filesystem` | رفع خطای فایل‌سیستم در حالت نوشتن | پشتیبان جدول + تأیید | اجرای دوباره `check_filesystem` |
| 12 | `rebuild_partition_and_format` | پاک کردن چیدمان، ساخت پارتیشن تازه و فرمت استاندارد | پشتیبان جدول + تأیید + نمایش ظرفیت نهایی | تست نوشتن/خواندن + ظرفیت |
| 13 | `full_surface_write_test` | نوشتن الگو روی کل سطح و خواندن آن؛ برای ظرفیت جعلی حکم قطعی می‌دهد ولی کل داده را پاک می‌کند | تأیید جدا با هشدار پاک شدن کامل | گزارش بلاک‌به‌بلاک خلاصه‌شده |

### گروه د — فریمور (ریسک ۳ — دو تأیید — فاز سوم، خارج از MVP اجرایی)

- ابزار `select_firmware_candidate` فقط نامزدی را برمی‌گرداند که خانواده کنترلر، شناسه حافظه و هش فایلش در بانک تست‌شده ثبت شده باشد؛ نامزد حدسی هرگز برنمی‌گردد
- ابزار `enter_factory_mode` دستگاه را با دستور اختصاصی همان خانواده وارد حالت کارخانه می‌کند و موفقیت ورود را قطعی بررسی می‌کند؛ شکست در این قدم یعنی توقف کامل، نه تلاش کور بعدی
- ابزار `flash_firmware` فایل انتخابی را می‌نویسد؛ حین کار درصد پیشرفت واقعی از ابزار گرفته می‌شود، نه از حدس مدل
- ابزار `verify_after_flash` بعد از راه‌اندازی دوباره دستگاه، ظرفیت، تست نوشتن/خواندن و پایداری اتصال را بررسی می‌کند و فقط خروجی همین ابزار ملاک اعلام موفقیت است

### گروه هـ — ابزارهای گفتگو و کنترل نشست (ریسک ۰)

- ابزار `explain_finding` یافته فنی را به زبان ساده و فارسی برای کاربر تبدیل می‌کند و سرنوشت داده‌ها را صریح می‌گوید
- ابزار `request_approval` کارت تأیید استاندارد می‌سازد: اقدام، دستگاه هدف، پیامد، سطح ریسک و دکمه‌های تأیید/لغو
- ابزار `ask_user_question` وقتی اطمینان تشخیص پایین است یا انتخاب واقعی با کاربر است، سؤال محدود و مشخص می‌پرسد
- ابزار `generate_repair_report` گزارش نهایی نشست را از داده‌های واقعی ابزارها می‌سازد؛ مدل در متن گزارش عدد جدید اختراع نمی‌کند
- ابزار `abort_session` نشست را در نقطه امن متوقف و وضعیت نیمه‌کاره را دقیق ثبت می‌کند

## ۸) درخت تصمیم تشخیص

منطق دسته‌بندی که مدل باید با داده ابزارها دنبال کند، نه با حدس آزاد:

- شاخه ظرفیت صفر یا بسیار کم: اول اتصال و شناسایی دوباره بررسی می‌شود؛ اگر ظرفیت پایدار و غیرواقعی بود، تشخیص محتمل خرابی فریمور/نگاشت کنترلر است و خروجی صادقانه این است: تعمیر نرم‌افزاری عمومی کافی نیست، خانواده کنترلر و وضعیت پشتیبانی فاز سوم اعلام می‌شود
- شاخه ظرفیت درست ولی درایو خام یا درخواست فرمت مداوم: اول سلامت خواندن نمونه‌ای و جدول پارتیشن بررسی می‌شود؛ جدول سالم + خواندن سالم یعنی خرابی فایل‌سیستم و مسیر تعمیر استاندارد گروه ج پیشنهاد می‌شود
- شاخه قفل نوشتن: اول پرچم نرم‌افزاری تست می‌شود؛ رفع شد و تست نوشتن سبز شد یعنی تمام؛ نشد یعنی قفل در سطح کنترلر/حافظه است و وعده رفع نرم‌افزاری داده نمی‌شود
- شاخه ظرفیت جعلی مشکوک: امتیاز ریسک بالا یعنی پیشنهاد تست سطح کامل با هشدار پاک شدن داده؛ نتیجه تست، ظرفیت واقعی را اعلام و چیدمان بر اساس ظرفیت واقعی ساخته می‌شود
- شاخه کندی و فایل خراب پراکنده: نقشه سلامت نمونه‌ای و سرعت ملاک است؛ نواحی مرده گسترده یعنی نشانه فرسودگی حافظه و گزارش، تعمیر را کم‌شانس اعلام می‌کند، نه اینکه فرمت را درمان جا بزند

## ۹) پشته فنی پیشنهادی

- بخش اصلی ویندوزی با سی‌شارپ و دات‌نت ۸ ساخته می‌شود؛ رابط کاربری دسکتاپ بومی، دسترسی تمیز به رابط‌های سیستمی ویندوز و انتشار تک‌فایل از مزیت‌های این انتخاب است
- بخش ابزارهای سطح پایین به‌صورت پردازه‌های جدا و کوچک پیاده می‌شوند تا خرابی یا هنگ یک ابزار، کل برنامه را نخواباند و هر ابزار جدا قابل تست باشد؛ ابزارهای نیازمند دسترسی سکتوری مستقیم در صورت نیاز با یک کمک‌کننده بومی کوچک همراه می‌شوند
- بخش ایجنت و ارائه‌دهنده مدل از رابط کاربری جداست و با تست واحد روی داده‌های ضبط‌شده از فلش‌های واقعی، بدون سخت‌افزار هم قابل تست است
- بخش ذخیره امن کلید فقط با سازوکار محافظت داده خود ویندوز انجام می‌شود؛ کلید هرگز در فایل تنظیمات ساده، رجیستری ساده یا لاگ نمی‌نشیند
- بخش بانک کنترلر و فریمور یک فایل داده محلی نسخه‌دار است که جدا از برنامه به‌روز می‌شود؛ هر رکورد فریمور هش و وضعیت تست و منبع دارد

ساختار پوشه پیشنهادی:

```text
src/
  App/            # UI (WPF or WinUI 3), approval cards, reports view
  Agent/          # agent loop, planner, session state, cost/step limits
  SafetyGate/     # risk policy, device-target revalidation, approval records
  ModelProvider/  # OpenAI-compatible client, tool-calling + structured fallback
  Tools/          # one folder per tool, JSON in/out contract, own tests
  Catalog/        # controller DB + firmware catalog (data, versioned)
  NativeHelper/   # optional small C++ helper for raw sector access
tests/
  Agent.Tests/        # replayed sessions, decision-tree cases
  SafetyGate.Tests/   # destructive-action-without-approval must fail
  Tools.Tests/        # virtual-disk backed tool tests
samples/
  faulty-cases/       # recorded diagnostics for 20+ known-fault devices
```

## ۱۰) فازبندی ساخت

### فاز ۱ — اسکلت و تشخیص (هفته ۱ تا ۲)

خروجی این فاز: برنامه‌ای که مدل کاربر را وصل می‌کند، فلش را پیدا می‌کند، همه ابزارهای گروه الف و هـ را اجرا می‌کند و گزارش تشخیص فارسی می‌دهد. معیار پذیرش: روی ۵ فلش سالم و خراب، گزارش درست و بدون هیچ نوشتنی روی دستگاه تولید شود.

### فاز ۲ — تعمیر امن و دروازه ایمنی (هفته ۳ تا ۴)

خروجی این فاز: ابزارهای گروه ب و ج پشت دروازه ایمنی، با کارت تأیید، پشتیبان جدول پارتیشن و راستی‌آزمایی بعد از هر قدم. معیار پذیرش: تست خودکار ثابت کند هیچ ابزار ریسک ۲ بدون تأیید ثبت‌شده اجرا نمی‌شود و دیسک سیستمی در هیچ مسیری قابل انتخاب نیست.

### فاز ۳ — سختی و انتشار (هفته ۵)

خروجی این فاز: مدیریت خطا و قطع اتصال وسط کار، سقف هزینه و قدم، گزارش قابل ذخیره، نصب‌کننده و تست روی حداقل ۲۰ نمونه خرابی معلوم با نرخ دسته‌بندی درست حداقل ۸۵٪. معیار پذیرش: هیچ نشستی بدون گزارش نهایی — موفق یا ناموفق — بسته نشود.

### فاز ۴ — بعد از MVP: فریمور خانواده‌به‌خانواده

خروجی این فاز: برای هر خانواده، جداگانه و با نمونه واقعی: شناسایی قطعی، ورود به حالت کارخانه، فلش، راستی‌آزمایی. معیار پذیرش هر خانواده مستقل است و تا خانواده‌ای پذیرش نگیرد، در برنامه «پشتیبانی‌شده» اعلام نمی‌شود.

## ۱۱) ریسک‌های اصلی و پاسخ طراحی

- ریسک انتخاب اشتباه دستگاه توسط کاربر یا مدل، با قانون شناسه یکتا و بررسی دوباره در لحظه اجرا پاسخ داده شده است
- ریسک توهم مدل در تشخیص، با قاعده «عدد و نتیجه فقط از خروجی ابزار» و درجه اطمینان اجباری در هر فرضیه پاسخ داده شده است
- ریسک هزینه دویدن مدل در چرخه بی‌پایان، با سقف قدم، سقف زمان و سقف هزینه برای هر نشست پاسخ داده شده است
- ریسک بریک شدن در فاز فریمور، با بانک فقط‌تست‌شده، هش اجباری فایل و دو تأیید پاسخ داده شده است؛ با این حال این ریسک صفر نمی‌شود و باید در محصول صادقانه اعلام شود
- ریسک حقوقی بانک فریمور واقعی است؛ فایل‌های فریمور سازنده‌ها را نباید بدون بررسی مجوز، داخل نصب‌کننده عمومی بازتوزیع کرد. مسیر امن نسخه اول: بانک فقط شامل فراداده و هش است و فایل از منبع کاربر یا مسیر مجاز تأمین می‌شود تا بررسی مجوز هر خانواده جدا انجام شود

## ۱۲) پرامپت آماده برای ایجنت کدنویس

بلوک زیر مستقل و قابل کپی است و برای شروع پیاده‌سازی فاز ۱ و ۲ به هر ایجنت کدنویسی داده می‌شود:

```text
Build a Windows desktop app (.NET 8, C#) implementing Phase 1 + 2 of the
attached MVP spec "USB Flash Repair Agent".

Hard rules (non-negotiable):
1. The LLM never executes raw commands. It may only call tools from the
   closed tool list in section 7 of the spec, each with the exact JSON
   in/out contract defined there.
2. Every tool has a risk level (0-3). Risk >= 2 must pass the SafetyGate:
   explicit recorded user approval + device unique-ID revalidation at
   execution time. The system disk and fixed internal disks must be
   impossible to select as destructive targets — enforce in code, not in
   the prompt. Add automated tests proving a risk-2 tool cannot run
   without a recorded approval.
3. Model connection is user-configured: Base URL + API Key + Model Name,
   OpenAI-compatible chat + tool-calling; structured-text fallback when
   tool-calling is unsupported. Store the API key ONLY via Windows DPAPI.
   Never log the key. Low fixed temperature for repair decisions.
   Per-session caps: max steps, max time, max estimated cost.
4. Agent loop: Observe (read-only tools) -> Diagnose (hypothesis +
   confidence) -> Plan (tool + reason + consequence per step) ->
   Approval gate -> Execute -> Verify with a real tool (never trust the
   model's claim) -> Report generated from tool outputs only.
5. Implement tools: list_usb_devices, get_device_details, get_disk_layout,
   check_filesystem, read_test_sample, detect_fake_capacity_risk,
   identify_controller, write_test_temp, measure_speed_sample,
   clear_readonly_flag, backup_partition_table, repair_filesystem,
   rebuild_partition_and_format, plus session tools explain_finding,
   request_approval, ask_user_question, generate_repair_report,
   abort_session. Firmware tools (section 7-D) are OUT of scope.
6. Tools run as separate processes with JSON stdin/stdout, individual
   timeouts, and summarized structured output (never raw dumps to the LLM).
7. UI: device picker that cannot confuse drives, live session timeline,
   approval card showing action + target device + consequence + risk,
   final Persian/English repair report exportable as a file.
8. Tests: agent decision-tree cases replayed from recorded diagnostics;
   SafetyGate tests; tool tests against virtual disks. No destructive
   code path may be exercised against a real physical disk in tests.

Deliver: runnable app, test results, and a short report separating
implemented vs planned, with exact file list. Follow the spec's section 8
decision tree for diagnosis categories.
```
